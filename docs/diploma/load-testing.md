# Load testing: read replica, CQRS read models, eventual-consistency lag

A deliberately light k6 study that produces three numbers for the thesis:

- **A.** how much read load the PostgreSQL streaming replica takes off the
  primary for workout-history browsing, and what that does to throughput and
  latency;
- **B.** how fast chart data is served from the precomputed analytics read
  models compared with what the main API computes (or returns raw) on request;
- **C.** how long a finished workout takes to become visible on the read
  side (outbox -> relay -> Kafka -> consumer) while the system is under load.

Everything (scripts, runner, seed, raw results) is in `load-tests/`. The
numbers below come from `load-tests/results/summary.md`, which
`load-tests/summarize.mjs` generates from the k6 `--summary-export` files.

## Methodology

**Hardware.** One laptop: Intel Core i9-13900H (14 cores / 20 threads),
32 GB RAM, Windows 11 Home, Docker Desktop 29.7.2 on the WSL 2 backend (the
Linux VM gets 15.5 GiB and 20 CPUs). Load generator, API, databases, Kafka,
analytics and the observability stack all share this one machine, so VU
counts are kept moderate (15-20 concurrent clients) and the runs are short.

**Stack.** `docker-compose.yml` of this commit with profiles `events` and
`observability`, started as a separate Compose project `loadtest`
(`load-tests/compose.loadtest.yml`: API on host port 3261, every other host
port moved, private subnet `172.28.50.0/24`, own image tags, env file
generated by `load-tests/make-env.sh` from `.env.example` with throwaway
secrets). NODE_ENV=production, one API process, one relay, one analytics
consumer, PostgreSQL 17 primary + one streaming standby, single-node Kafka.
**Tracing is off** (`OTEL_EXPORTER_OTLP_ENDPOINT` empty): span export would add
work that is not part of what is measured. Prometheus/Grafana/Loki/Alloy run,
as they would in the demo.

**Load generator.** `grafana/k6:1.3.0`, run with `docker compose run k6` on the
internal `private` network, so it calls `http://api:3000` directly with no
host port, Windows port proxy or tunnel in the path. Closed model without
think time: each VU sends its next request as soon as the previous one
answered, i.e. the numbers are throughput and latency at saturation for that
many concurrent clients.

**Rate limiting.** The API trusts one proxy hop in production and its global
throttler allows 120 requests per minute per client IP. A load test from one
container would measure the limiter, not the server. k6 therefore sends a
distinct `X-Forwarded-For` address per request, modelling many clients behind
the tunnel. The limiter itself is unchanged and still runs on every request.

**Data.** `load-tests/seed/seed-loadtest.sql`, deterministic, written straight
into the primary (about 3 s): 50 users (`lt001..lt050@loadtest.example.com`,
password `LoadTest!2026`, bcrypt cost 10), each with 150 completed workouts
spread evenly over the last 18 months (5 exercises x 3-4 sets, 15-20 sets per
workout, slowly rising weights) and one body-metric entry per week (78).
Total 7,500 workouts, 131,250 sets, 3,900 body metrics, plus the 17 workouts of
the dump. `scripts/backfill-analytics-events.ts` (Compose service `backfill`)
then enqueued 11,417 outbox events; the relay and the analytics consumer
drained them in about 2 minutes, so the read models hold the same history.
Users 1-20 only read (they never write, so `readerFor()` always routes them to
the replica when one is configured); users 21-50 are the writers of C.
Access tokens come from the real `POST /auth/login` in k6 `setup()`.

**Procedure** (`load-tests/run.sh`, all of it `load-tests/run-all.sh`). For
each run: wait until no container of another Compose project runs (the
developer's own `hittrackerbackend` project is allowed and was up the whole
time), recreate the API container for the arm (fresh process, empty
read-your-writes map), 15 s warm-up with the same script (not recorded),
snapshot `pg_stat_database` of `nestdb` on primary and standby, 60 s measured
run, snapshot again, and for C export the outbox/consumer timestamps. Every
configuration ran **3 times; the median run is reported** (by throughput for
A/B, by lag p50 for C), with the other runs listed for spread. The A arms were
interleaved (replica, single, replica, ...) so drift affects both equally.
An idle 60 s window measures the background activity (relay polling,
exporter scrapes).

| measurement | VUs | duration | what runs |
| --- | ---: | --- | --- |
| A with replica | 20 | 60 s | history list 40 % / calendar dates 20 % / details 40 % |
| A single node | 20 | 60 s | same, API started with `DATABASE_REPLICA_URL=""` (`load-tests/compose.single-node.yml`) |
| B | 18 + 2 | 60 s | 18 VUs rotate the six single-request endpoints, 2 VUs loop the weekly-volume composite |
| C | 15 + up to 8 | 60 s | the B mix as background + 30 finished workouts per minute |

**Measured quantities.** Per endpoint a k6 Trend (latency, p50/p95/p99),
a Counter (req/s = count / 60 s; setup traffic excluded), a Rate (errors =
unexpected status) and the body size. Database work per server comes from
`pg_stat_database` deltas: `xact_commit` (every statement outside an explicit
transaction is one transaction, so this is a query count) and `tup_returned`
(rows read by scans). `pg_stat_statements` is not preloaded in this stack, so
per-statement numbers are not available.

**Other containers during the measurements.** Only the developer's own
project `hittrackerbackend` (api, postgres, minio: idle, about 0 % CPU in
every `docker stats` snapshot) ran next to `loadtest`. Another agent's
throwaway project `featatrace` was running when the study started; the runner
waited until it was gone, and every run's `otherProjectsDuringRun` field (in
its `.meta.json`) is empty. Processes on the Windows host itself (outside
Docker) were not controlled; see threats to validity.

Latency in ms over all three endpoints (per-endpoint rows are in
`summary.md`: list and details cost about the same, calendar dates about
60 % of that). CPU is a `docker stats` snapshot 30 s into the run, 100 % = one
core. Idle baseline: primary 6.5 tx/s, replica 0.6 tx/s.

Three unplanned 30 s re-runs right after the series gave 884 and 801 req/s
(replica) and 902 req/s (single), p95 31-35 ms in both arms, with the primary
at 8 tx/s while the replica served 1,175-1,312 tx/s.

**Interpretation.** The routing works as designed: with
`DATABASE_REPLICA_URL` set, every history query of these read-only users went
to the standby, and the primary stayed at its idle level (relay polling and
the exporter). Its CPU, locks and buffer cache stay free for writes. That is
the defensible number: **about 99 % of the read load moved off the primary**.
On this machine the replica does *not* raise throughput or lower latency.
The only single-threaded component, the one API process, sits at 100 % of a
core in every run, so the database is not the bottleneck in either arm, and
primary and replica share the same 20 vCPUs of one VM anyway. The replica
arm's median is lower (458 vs 626 req/s), but its three runs drifted downwards
(612 -> 458 -> 338) while the interleaved single-node runs did not, and in the
later re-runs both arms reached the same ~800-900 req/s. The difference is
within this setup's noise and must not be read as "the replica is slower". A
throughput benefit needs a setup where the database is the bottleneck:
several API instances, or the replica on separate hardware.

**Finding (not fixed):** `sets.workout_id`, `sets.exercise_id` and
`workouts.user_id` have no indexes (only the primary keys exist). Every
history list, detail and exercise-sets request therefore scans the whole
`sets` table: ~110,000 rows per request here, and 4.15 billion rows in 60 s in
the single-node arm (`tup_returned`). `EXPLAIN ANALYZE` of one detail query
shows `Seq Scan on sets ... Rows Removed by Filter: 131307` taking 7.7 ms.
This is why PostgreSQL burns ~3 cores for ~1,000 queries/s. The cost grows
linearly with the total number of sets of *all* users. A migration adding
those three indexes is the obvious follow-up; it is a schema change, so it
was left out of this study.

### B. CQRS: computed on request vs read models (18 + 2 VUs, 60 s, replica arm)

The original B weekly-composite numbers used a rolling 84-day window that included a 13th partial ISO week. They are superseded by the three corrected, indexed runs below; both paths now use the same 12 ISO weeks, beginning on the Monday 11 weeks before the current week (UTC).

What each endpoint computes, for a user with 150 workouts / ~2,600 sets over
18 months:

- `old_exercise_sets` - `GET /workouts/exercise/:id/sets`: every raw set of
  one exercise (~330 rows, joined with workouts, ordered). The old mobile
  chart plots weight against reps.
- `new_exercise_progress` - `GET /analytics/me/exercises/:id/progress`: one
  precomputed row per training day (top set, e1RM, volume), a primary-key
  range read. This is a different chart product; latency and payload compare
  what the exercise screen downloads, not equivalent plotted data.
- `old_body_metrics` - `GET /users/me/body-metrics?from&to` (365 days): the
  main API reads all rows up to `to` and computes first/current/latest/change
  per metric on every request.
- `new_body_metrics` - `GET /analytics/me/body-metrics?from&to`: the
  precomputed timeline points (without the summary fields).
- `new_summary` - `GET /analytics/me/summary`: this/last week, streak, PR
  count, last workout; four small indexed reads.
- `new_weekly_volume` - `GET /analytics/me/weekly-volume?weeks=12`.
- `old_weekly_volume_composite` - the same 12 ISO weeks without a read
  model. The write API has no aggregate endpoint, so the client lists from
  the oldest included Monday (`GET /workouts/history?from=...&limit=50`) and
  fetches each workout's details (20 in parallel with k6 `http.batch`, 6 per host) to sum
  the volume. Latency = list + slowest detail.

All `new_*` calls go through the main API proxy (`/analytics/*` -> analytics
service), i.e. one extra HTTP hop; the `old_*` calls read the replica.

Median corrected run `after-b-cqrs-3`:

| endpoint | req/s | p50 | p95 | p99 | avg payload | errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| old_exercise_sets | 78.5 | 30.4 | 66.3 | 100.2 | 46.8 KiB | 0 % |
| new_exercise_progress | 78.5 | 41.0 | 66.4 | 85.6 | 8.2 KiB | 0 % |
| old_body_metrics | 78.5 | 25.2 | 61.1 | 93.4 | 11.6 KiB | 0 % |
| new_body_metrics | 78.5 | 40.8 | 65.4 | 88.3 | 6.5 KiB | 0 % |
| new_summary | 78.5 | 37.6 | 58.3 | 81.8 | 0.5 KiB | 0 % |
| new_weekly_volume | 78.5 | 36.6 | 58.2 | 81.6 | 1.2 KiB | 0 % |
| old_weekly_volume_composite (21 requests) | 9.4 | 187.0 | 389.8 | 499.4 | 62.1 KiB | 0 % |

p95 of the corrected runs (ms): exercise sets 76/93/66 vs progress 74/84/66;
body metrics 68/83/61 vs 72/82/65; summary 65/75/58; weekly volume 68/76/58 vs
composite 362/559/390. CPU 30 s into the median run: API 103 %, replica 27 %, analytics 30 %,
primary 14 %.

**Interpretation.** Per single request the read models are not consistently
faster here. At 150 workouts per user, the saturated API process dominates
latency and the analytics proxy adds a hop. For the same 12 ISO-week volume
chart, the read model uses **one request instead of 21, 5.1x lower p50
(6.7x lower p95), and about 52x less data**. The new exercise endpoint
downloads 8.2 KiB of daily aggregates rather than 46.8 KiB of raw sets,
but those endpoints serve different charts. The new indexes remove the old
exercise query's full-table scan (see [indexes.md](indexes.md)); the price of
the read models' asynchronous updates is measured in C.

### C. Eventual-consistency lag under load (15 background VUs + writer)

The writer finishes 30 workouts per minute (`POST /workouts/start`, 5 x
`POST /workouts/:id/sets`, `POST /workouts/:id/finish`, users lt021-lt050) and
then polls `GET /analytics/me/summary` every 50 ms until
`lastWorkout.workoutId` is the finished workout. The background VUs run the
B mix. Median run `c-lag-2`:

| measure | n | p50 | p95 | p99 | max |
| --- | ---: | ---: | ---: | ---: | ---: |
| finish response -> visible in `/analytics/me/summary` (k6) | 31 | 326 | 531 | 542 | 545 |
| outbox `occurred_at` -> relay `published_at` (DB) | 31 | 334 | 498 | 520 | 520 |
| `published_at` -> consumer `processed_at` (DB) | 31 | 5 | 12 | 13 | 13 |
| `occurred_at` -> `processed_at` (DB total) | 31 | 336 | 500 | 523 | 523 |

All runs (p50/p95/max, ms): 397/543/604, 326/531/545, 273/520/530. No
workout took longer than 30 s (0 timeouts out of 93 workouts). Background
during C: 103 req/s per endpoint, p95 35-50 ms, 0 errors; the write endpoints
had p95 110-145 ms.

**Interpretation.** Under load, charts typically lag a finished workout by
about a third of a second, and never by more than ~0.6 s. The DB timestamps
show where the time goes. They share the Docker VM clock; `occurred_at` is
the start of the finish transaction and `processed_at` the start of the
consumer transaction. The relay's 500 ms outbox poll interval
(`RELAY_POLL_INTERVAL_MS`) accounts for nearly all of the lag, while Kafka
plus the idempotent projection typically take 5 ms. The ~15 ms quoted in
`analytics-cqrs.md` is that last part. The lag is bounded by poll interval +
publish + projection. A shorter poll interval (or LISTEN/NOTIFY instead of
polling) would cut it, at the price of more idle queries on the primary. The
k6 figure has a resolution of the 50 ms poll interval plus one poll round
trip.

## After LISTEN/NOTIFY (T15)

T15 (`OutboxService.enqueue` sends `pg_notify('outbox_events', '')` in the
enqueuing transaction; the relay keeps a dedicated `LISTEN outbox_events`
connection to the primary and wakes its batch loop immediately, with a
5 s fallback poll, see `docs/diploma/outbox.md`) re-ran scenario C with the
same parameters as the T12 study above: same seed (50 users, 7,500 workouts),
same script (`scenarios/c-lag.js`), same arm (`replica`), 15 background VUs
+ writer (users lt021-lt050), 15 s warm-up, 60 s measured, 3 runs, median by
k6 lag p50. Raw results: `load-tests/results/c-notify-{1,2,3}.{json,meta.json,lag.csv,log,docker-stats.txt}`;
`load-tests/summarize.mjs` now reports both the before (`c-lag`) and after
(`c-notify`) groups under "C. Eventual-consistency lag under load" in
`load-tests/results/summary.md`.

**Before (T12, median run `c-lag-2`) vs after (median run `c-notify-1`), ms:**

| measure | n | p50 before | p50 after | p95 before | p95 after | p99 before | p99 after | max before | max after |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| finish response -> visible in `/analytics/me/summary` (k6) | 31 | 326 | **59** | 531 | **91.5** | 542 | **95.5** | 545 | **97** |
| outbox `occurred_at` -> relay `published_at` (DB) | 31 | 334 | **41** | 498 | 162 | 520 | 230 | 520 | 230 |
| `published_at` -> consumer `processed_at` (DB) | 31 | 5 | 3 | 12 | 5 | 13 | 7 | 13 | 7 |
| `occurred_at` -> `processed_at` (DB total) | 31 | 336 | **44** | 500 | 164 | 523 | 234 | 523 | 234 |

All runs (p50/p95/max, ms), after: 59/92/97 (`c-notify-1`), 81/105/109
(`c-notify-2`), 51/99/108 (`c-notify-3`) vs before: 397/543/604, 326/531/545,
273/520/530. 92 workouts finished across the 3 after-runs (31/30/31), 0
timeouts, same as before (93 workouts, 0 timeouts).

**Relay wakeup reasons.** Read from the relay's own `/metrics`
(`outbox_relay_wakeups_total{reason}`) right before tearing the stack down,
so the counts are cumulative since the relay container started (backfill of
11,417 events by direct `INSERT`, which bypasses `enqueue`/`pg_notify` and so
only ever woke the relay via the timer, plus the seed/drain wait and all 3
measured runs): `reason="notify"` 232, `reason="timer"` 72. During the
measured runs themselves (93 workout finishes, each one `NOTIFY`) the large
majority of wakeups are `notify`; the timer only matters for the bulk
backfill and the idle gaps between runs, exactly as designed.

**Headline: p50 lag dropped 326 ms -> 59 ms (5.5x), p95 531 ms -> 91.5 ms
(5.8x), max 545 ms -> 97 ms (5.6x).** The DB-total breakdown shows why:
`occurred_at -> published_at` (the relay's share) fell from 334 ms p50 to
41 ms p50 - almost exactly the poll-interval component predicted in the T12
interpretation - while `published_at -> processed_at` (Kafka + consumer) is
unchanged (~3-5 ms p50 both before and after, as expected: T15 does not touch
that path). The p95/p99/max of the relay's own share (162/230/230 ms) stay
well above its own median (41 ms): `processBatch` still publishes claimed
rows one at a time inside a single transaction, so when several
`workout.finished` events commit close together and share one wakeup, the
last ones in that batch wait behind the earlier ones' Kafka round trips -
the coalescing this change adds (see `docs/diploma/outbox.md`) trades a few
such tail-latency events for never running two batches concurrently. This is
still 2-3x faster at p95/p99/max than the old poll-only relay.

One after-run (`c-notify-1`, the picked median) shows an outlier
`postgres-replica` CPU reading (367 % vs 80-92 % in every other C run, before
or after, see `load-tests/results/c-notify-1.docker-stats.txt`) and higher
write-endpoint p95s (144-216 ms vs 110-145 ms before); `c-notify-2`/`-3` show
normal replica CPU and consistent low lag, so this looks like the
one-machine/WSL2 noise already called out below rather than a regression
caused by holding one extra `LISTEN` connection.

## Threats to validity

- **One machine.** Load generator, API, both PostgreSQL servers, Kafka,
  analytics and observability share one laptop's CPUs. The results are
  relative comparisons on this box, not capacity figures for production.
  Separate hardware per database is exactly what would make a replica pay off
  in throughput.
- **Docker Desktop on Windows (WSL 2).** CPU and memory are virtualised, and
  the Windows host ran other processes: other agents' builds and tests on the
  same laptop were not controlled, and the `hittrackerbackend` project was
  running (idle). Run-to-run variance is large: A ranged from 338 to 902 req/s
  for the same script, so only differences well beyond that range mean
  anything. That is why 3 runs, the median and the spread are reported.
- **Single API process.** The Node.js API saturates one core in every
  scenario, so the latencies partly measure the API's event loop rather than
  the databases. With several API instances the database side would matter
  more.
- **Warm caches, small data.** There is a 15 s warm-up, and the whole data set
  (the `sets` table is 8 MB) fits in shared buffers, so no disk I/O is
  measured. 50 users x 150 workouts is far below a real user base; at scale
  the full-table scans (finding in A) would dominate.
- **Synthetic, closed-model load.** No think time and a fixed endpoint mix,
  while real clients are open-model and mostly idle. The same 20 reader
  accounts are reused, and the `X-Forwarded-For` rotation takes the per-IP
  throttler out of the measurement.
- **Counters are database-wide.** The `pg_stat_database` deltas include k6
  `setup()` (20-50 logins, ~80 fixture reads), relay polling, exporter scrapes
  and the runner's own snapshot connections. These are small next to the load
  (idle 6.5 tx/s vs ~1,000 tx/s) but not zero. `pg_stat_statements` is not
  enabled, so per-query numbers are unavailable.
- **Tracing off.** The numbers are without OpenTelemetry export; with 100 %
  sampling to Jaeger they would be somewhat worse.
- **The k6 lag measurement** starts at the finish *response* and ends at the
  first poll that sees the workout (resolution ~50 ms plus one round trip). The
  DB cross-check uses transaction start times.

## Reproducing

From the repository root, in Git Bash (POSIX sh) on Windows or any
Linux/macOS shell with Docker Compose v2:

```sh
sh load-tests/make-env.sh                  # throwaway load-tests/.env.loadtest
export MSYS_NO_PATHCONV=1                  # Git Bash only
C="docker compose -p loadtest --env-file load-tests/.env.loadtest \
  -f docker-compose.yml -f load-tests/compose.loadtest.yml \
  --profile events --profile observability --profile loadtest"
$C build api analytics analytics-migrate migrate
$C up -d --no-build                        # run again if the replica was slow to become healthy
$C run --rm -T psql -h postgres -f /work/seed/seed-loadtest.sql   # ~3 s
$C run --rm --no-deps -T backfill          # then wait until the consumer has drained (~2 min):
$C exec -T postgres psql -U postgres -d analytics -tAc 'select count(*) from processed_events'
sh load-tests/run-all.sh                   # ~25 min: idle, 3x A (both arms), 3x B, 3x C
node load-tests/summarize.mjs              # -> load-tests/results/summary.md
$C down -v                                 # always, also after a failure
rm load-tests/.env.loadtest
```

From PowerShell, run the same steps through Git's sh
(`& "C:\Program Files\Git\bin\sh.exe" load-tests/run-all.sh`), or call k6
directly, for example
`docker compose -p loadtest --env-file load-tests/.env.loadtest -f docker-compose.yml -f load-tests/compose.loadtest.yml --profile loadtest run --rm k6 run --summary-export results/a.json scenarios/a-replica.js`
